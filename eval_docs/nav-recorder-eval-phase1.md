# nav-recorder 第一階段評估指標

階段編號沿用流程報告。分級：關鍵 › 重要 › 一般 › 次要 › 不關鍵。

## 評分規則

**一輪評估**
- 一輪 = 20 個真實任務，加上跑一次回歸測試集。以任務數切，不以週數切；以每週 8–9 個任務計，約 2–3 週一輪。
- 任務分三種標記：
  - **真實**：日常開發中實際交付的任務。
  - **測試**：固定的回歸測試集，每輪跑一次、內容不變。包含各 Checklist 的情境，以及為了補足樣本而設計的任務。
  - **除錯**：MVP 優化期間臨時為了除錯而跑的任務，不計入任何指標。
- 每個指標用哪種樣本，見總覽表的「樣本」欄。
- 對照組：每輪從真實任務抽 3–4 個，在不用工具的情況下各跑 1 次。

**Rubric**
- 1–5 分，5 分最好。
- 由 5 分往下逐級比對，符合的第一級即為得分。
- 區間一律寫明不等式，相鄰兩級的區間不重疊。
- 標有「上限」的條件，先依數值給分，再取它與上限中較低的分數。
- 標有「否決」的條件，只要符合就直接給 1 分，不必再比對其他等級。
- 整輪合計：分子、分母各自加總後算一次，每個指標每輪只有一個分數。每個任務的原始紀錄都要保留，分數變差時用來回查是哪幾個任務拉低的。
- 門檻分兩種（見總覽表的「門檻」欄）：
  - **次數**：分母是任務數或 recipe 數的指標，用每輪發生的次數訂等級。每輪的任務數固定，所以次數可以跨輪比較。
  - **百分比**：分母是請求數、步驟數這類樣本量大的指標。分母小於 10 時記為「樣本不足」。
- 次數型指標的分母為 0 時（例如這輪沒有任何依賴既有資料的 recipe），也記為「樣本不足」。

**Checklist**
- 每一項只判「通過／不通過」，沒有部分給分。
- 整題結果記為「通過項數 / 總項數」，並列出未通過的項目。
- 不換算成 1–5 分。

## E2E

目的：整個工具讓開發任務更快、更省。

### E-1 加速倍數 · 關鍵 · Rubric

- **量法**：每輪從真實任務抽 3–4 個，在不用工具的情況下各跑 1 次對照組。每個抽樣任務的加速倍數 = 對照組耗時 ÷ 實驗組耗時，取這幾個任務的中位數。耗時從收到任務算到瀏覽器停在目標畫面、可以開始測試為止。
- **資料來源**：transcript 時間戳、對照組。

| 分數 | 條件 |
|---|---|
| 5 | 加速倍數 ≥ 3.0 |
| 4 | 2.0 ≤ 加速倍數 < 3.0 |
| 3 | 1.5 ≤ 加速倍數 < 2.0 |
| 2 | 1.0 ≤ 加速倍數 < 1.5 |
| 1 | 加速倍數 < 1.0（比不用工具還慢） |

### E-2 token 節省量 · 重要 · Rubric

- **量法**：用 E-1 的同一批抽樣任務。每個任務的節省比例 = (對照組 token − 實驗組 token) ÷ 對照組 token，取中位數。token 含輸入與輸出。
- **資料來源**：transcript、對照組。

| 分數 | 條件 |
|---|---|
| 5 | 節省比例 ≥ 50% |
| 4 | 30% ≤ 節省比例 < 50% |
| 3 | 15% ≤ 節省比例 < 30% |
| 2 | 0% ≤ 節省比例 < 15% |
| 1 | 節省比例 < 0%（用得比不用工具還多） |

### E-3 人為介入次數 · 重要 · Rubric

- **量法**：每個任務中使用者被 agent 提問、或需要親自操作的次數，取任務集平均。親自操作包括重載 extension、手動登入、手動導航、修改 config。不計入：任務開始時交付需求；新角色第一次出現時的 newActor 確認。
- **資料來源**：transcript。

| 分數 | 條件 |
|---|---|
| 5 | 平均 = 0 次 |
| 4 | 0 < 平均 ≤ 0.5 次 |
| 3 | 0.5 < 平均 ≤ 1 次 |
| 2 | 1 < 平均 ≤ 2 次 |
| 1 | 平均 > 2 次 |

### E-4 各階段 token 佔比 · 一般 · Checklist

- **量法**：把每個任務的 token 依工具呼叫切到階段 2–6。這題是診斷用的報表，不評好壞，只檢查報表是否完整可用。
- **資料來源**：transcript。

| # | 檢查項 | 通過條件 |
|---|---|---|
| 1 | 每個工具呼叫都歸到一個階段（2–6 或「階段外」） | 未歸類的呼叫數 = 0 |
| 2 | 各階段 token 加總與任務總 token 一致 | 差額 ≤ 1% |
| 3 | 標出佔比最高的階段 | 報表中有標示 |
| 4 | 佔比最高的階段列出最貴的前三種工具呼叫 | 報表中有列出 |

## 1 背景錄製

目的：使用者不用做任何事，就把到達目標的操作完整錄下來。

### 1-1 請求完整率 · 關鍵 · Rubric

- **量法**：同一段操作同時開 DevTools 匯出 HAR。
  - 分母：HAR 中白名單 origin、且發自 active tab 的 fetch／XHR 請求數。
  - 分子：raw 中能一對一對應的請求數。對應條件是 method 與 URL 相同，時間差 ≤ 2 秒。
  - 完整率 = 分子 ÷ 分母。
  - 寫入請求：method 不是 GET／HEAD／OPTIONS，且未命中 readOnlyPatterns。
- **資料來源**：raw 日檔、HAR。

| 分數 | 條件 |
|---|---|
| 5 | 完整率 = 100% |
| 4 | 98% ≤ 完整率 < 100% |
| 3 | 95% ≤ 完整率 < 98% |
| 2 | 90% ≤ 完整率 < 95% |
| 1 | 完整率 < 90% |
| 上限 | 漏掉 1 筆寫入請求 → 最高 2 分；漏掉 ≥ 2 筆 → 1 分 |

### 1-2 操作類型覆蓋 · 重要 · Checklist

- **量法**：每項操作在測試站做一次，檢查 raw 中的事件。
- **資料來源**：raw 日檔、.bodies 側檔。

| # | 操作 | 通過條件 |
|---|---|---|
| 1 | 點擊按鈕 | 有 click 事件，帶 role、accessibleName，且至少一組 selector |
| 2 | 在輸入框按 Enter 送出 | 有 Enter 事件 |
| 3 | 下拉選單或 checkbox 改值 | 有 change 事件 |
| 4 | SPA 內部換頁（pushState） | 有 navigation 事件（historyStateUpdated） |
| 5 | 網址列輸入網址整頁載入 | 有 navigation 事件，transitionType = typed |
| 6 | 重新整理頁面 | 有 navigation 事件，transitionType = reload |
| 7 | fetch 請求 | 有 request 事件，含 status 與 response body |
| 8 | XHR 請求 | 有 request 事件，含 status 與 response body |
| 9 | response body ≥ 512 字元 | 事件行 responseBody = null、有 responseBodyRef，且側檔有對應 sha1 |
| 10 | 開新分頁操作同一站 | 新分頁的事件有被錄 |
| 11 | 同分頁回登入頁重新登入 | 登入請求有被錄，且後續請求的 authSources 指向它 |
| 12 | 讓 service worker 休眠後再操作 | 休眠後的事件有被錄 |
| 13 | 背景分頁發出的請求 | raw 中**沒有**這些事件 |
| 14 | 非白名單 origin 的請求 | raw 中**沒有**這些事件 |
| 15 | pause 狀態下的操作 | raw 中**沒有**這些事件 |

### 1-3 錄不到的次數 · 重要 · Rubric

- **量法**：只看使用者確實在 Chrome 操作過目標畫面之後的 capture-recent 呼叫，數一輪中回 `E_NO_EVENTS` 或 `E_NO_ANCHOR` 的次數。排除使用者根本沒操作、或 `--target-url` 本身寫錯的呼叫（人工判定）。
- **資料來源**：capture-recent 錯誤碼。

| 分數 | 條件 |
|---|---|
| 5 | 0 次 |
| 4 | 1 次 |
| 3 | 2 次 |
| 2 | 3–4 次 |
| 1 | ≥ 5 次 |

## 2 查知識庫、找目標畫面

目的：不讀程式碼就找到目標畫面與進入方式。

### 2-1 退回讀程式碼的任務數 · 關鍵 · Rubric

- **量法**：一輪 20 個真實任務中，agent 為了找目標 route 或進入方式，讀了專案原始碼（router、選單、權限設定檔）的任務數。依 transcript 中對這類檔案的 Read／Grep 判定。另外分開記錄前 10 個與後 10 個任務各有幾個，供 K-2 參考，不計分。
- **資料來源**：transcript。

| 分數 | 條件 |
|---|---|
| 5 | ≤ 1 個任務 |
| 4 | 2–3 個任務 |
| 3 | 4–6 個任務 |
| 2 | 7–10 個任務 |
| 1 | ≥ 11 個任務 |

### 2-2 目標 route 首選錯誤數 · 重要 · Rubric

- **量法**：「首選」是 agent 第一次傳給 `capture-recent --target-url` 或 `list --target-url` 的 path。數一輪 20 個真實任務中，首選與人工標註不一致的任務數。
- **資料來源**：transcript、人工標註。

| 分數 | 條件 |
|---|---|
| 5 | 0 個任務 |
| 4 | 1 個任務 |
| 3 | 2–3 個任務 |
| 2 | 4–6 個任務 |
| 1 | ≥ 7 個任務 |

### 2-3 既有 recipe 漏抓 · 一般 · Checklist

- **量法**：preconditions/ 預先放一份某畫面的已驗證 recipe，再依下列情境各交付一次任務。
- **資料來源**：transcript、preconditions/。

| # | 情境 | 通過條件 |
|---|---|---|
| 1 | 目標 path 與 recipe 的 target 完全相同 | `list` 回 matched: exact，agent 沿用、沒有呼叫 capture-recent 產生新草稿 |
| 2 | 錄製中的目標 URL 帶 query string | agent 去掉 query 後查到，沿用 |
| 3 | 使用者用畫面名稱描述，沒給 path | 經 `routes find` 找到 path，`list` 命中，沿用 |
| 4 | 目標是 recipe target 的子路徑 | `list` 回 matched: prefix，agent 寫出可否沿用的理由 |
| 5 | 目標與 recipe 同區段、但是不同畫面 | `list` 回 matched: section，agent 沒有誤用既有 recipe |

## 3 認領與蒸餾

目的：從混雜的錄製裡，機械地蒸餾出正確的最小 recipe。

### 3-1 既有資料依賴漏判 · 關鍵 · Rubric

- **量法**：人工標註每份 recipe 的目標畫面，是否依賴「沒有任何步驟會建立的既有資料」。
  - 漏判：標註為依賴，shape 卻是 `navigation`。
  - 誤報：標註為不依賴，shape 卻是 `navigation-existing-data`。
  - 數一輪中的漏判次數與誤報次數。回歸測試集要放入依賴既有資料的任務，確保分母不為 0。
- **資料來源**：capture-recent 的 shape、人工標註、換機器重播結果。

| 分數 | 條件 |
|---|---|
| 5 | 漏判 0 次 且 誤報 0 次 |
| 4 | 漏判 0 次 且 誤報 ≥ 1 次 |
| 3 | 漏判 1 次 |
| 2 | 漏判 2 次 |
| 1 | 漏判 ≥ 3 次 |

### 3-2 保留步驟準確率／召回率 · 重要 · Rubric

- **量法**：以整輪所有 recipe 合計。召回率優先，因為少一步會導致重播失敗，多一步通常只是多花時間。
  - 召回率 = kept 中屬於標註「必要寫入」的數量 ÷ 標註的必要寫入總數。
  - 準確率 = kept 中屬於必要寫入的數量 ÷ kept 總數。
- **資料來源**：evidence.kept、人工標註。

| 分數 | 條件 |
|---|---|
| 5 | 召回率 = 100% 且 準確率 = 100% |
| 4 | 召回率 = 100% 且 90% ≤ 準確率 < 100% |
| 3 | 召回率 = 100% 且 準確率 < 90% |
| 2 | 90% ≤ 召回率 < 100% |
| 1 | 召回率 < 90% |

### 3-3 該留卻被丟 · 重要 · Checklist

- **量法**：每項準備一段含該類請求的錄製，跑 capture-recent，檢查 kept、dropped 與 warnings。
- **資料來源**：capture-recent 回傳的 evidence、warnings、pendingDecisions。

| # | 情境 | 通過條件 |
|---|---|---|
| 1 | 切換公司／租戶的呼叫，參數只在 path 上、body 為空 | 在 kept；或在 dropped.authRefresh 且 warnings 明確列出它 |
| 2 | 建立資料後，下一個寫入在 path 上帶新 id | 兩筆都在 kept |
| 3 | 寫入請求的 response 值只出現在目標頁 URL | 在 kept |
| 4 | 寫入請求回 4xx 後重送成功 | 失敗那筆在 dropped.failed，成功那筆在 kept |
| 5 | 真正的 token refresh | 在 dropped.authRefresh，**不在** kept |
| 6 | anchor 之後的寫入 | 在 dropped.afterAnchor |
| 7 | 本任務需要的前置寫入，落在被排除的段落 | 出現 excludedSteps 決策 |

### 3-4 草稿未一次通過數 · 重要 · Rubric

- **量法**：
  - 「一次通過」：agent 只處理 pendingDecisions，並填寫必填語意欄位（verify、description、選 finalNavigation、修剪 targetHint），沒有新增、刪除或修改任何 api 步驟、參數值或 capture，就通過自我驗證。
  - 數一輪中沒有一次通過的草稿數。沿用既有 recipe 的任務不產生草稿，不計入。
  - 每份草稿被改的步驟數另外記錄，不計分。
- **資料來源**：save-recipe 前的草稿副本（需補紀錄）與最終 recipe 的 diff。

| 分數 | 條件 |
|---|---|
| 5 | ≤ 1 份 |
| 4 | 2–3 份 |
| 3 | 4–5 份 |
| 2 | 6–8 份 |
| 1 | ≥ 9 份 |

## 4 補完與自我驗證

目的：在動程式碼之前，證明 recipe 本身是對的。

### 4-1 假通過次數 · 關鍵 · Rubric

- **量法**：自我驗證通過的 recipe，在系統未被改動的條件下（實作前，或在乾淨的分支），由另一個 agent session 重播一次。數一輪中重播失敗的次數。
- **資料來源**：重播的 execute session 紀錄、verify 結果。

| 分數 | 條件 |
|---|---|
| 5 | 0 次 |
| 4 | 1 次 |
| 3 | 2 次 |
| 2 | 3–4 次 |
| 1 | ≥ 5 次 |

### 4-2 驗證造出的垃圾資料 · 重要 · Rubric

- **量法**：每次自我驗證（含 probe）結束後，抽查測試站資料庫中這次建立的資料。
  - 無法辨識：從欄位值看不出是 recipe 建立的，例如沒有固定前綴或 faker 的可辨識特徵。
  - 影響他人：造成其他使用者畫面出現錯誤資料，或造成唯一性衝突。
- **資料來源**：測試站資料庫抽查。

| 分數 | 條件 |
|---|---|
| 否決 | 任一筆影響他人 → 1 分 |
| 5 | 全部可辨識，且可用 recipe 名稱一次查出全部 |
| 4 | 全部可辨識，但需要逐筆找 |
| 3 | 每次驗證平均 ≤ 1 筆無法辨識 |
| 2 | 每次驗證平均 > 1 筆無法辨識 |
| 1 | （由否決條件給分） |

## 5 三段式執行迴圈

目的：穩定地把 recipe 重播到 done。

### 5-1a halt 紀錄完整性 · 關鍵 · Checklist

- **量法**：5-1b 的前提。第 1–3 項全部通過，5-1b 才評分。
- **資料來源**：halt 紀錄表、execute session 紀錄。

| # | 檢查項 | 通過條件 |
|---|---|---|
| 1 | 每次 halt 都有紀錄 | halt 次數 = 紀錄筆數 |
| 2 | 紀錄欄位齊全 | 每筆都有 recipe 名稱、步驟序號、reason、lastError 原文 |
| 3 | 每筆都有人工判定類別 | 類別只屬於五類之一：recipe 本身錯／環境／資料衝突／Playwright 不穩／依賴了要改動畫面的 DOM |
| 4 | 「recipe 本身錯」寫出錯在哪 | 每筆都指出出錯的欄位或步驟 |
| 5 | 「依賴了要改動畫面」有修正終點 | 每筆都記錄修改後的 finalNavigation |

### 5-1b recipe 造成的 halt 次數 · 關鍵 · Rubric

- **量法**：數一輪中判定為「recipe 本身錯」或「依賴了要改動畫面的 DOM」的 halt 次數。
- **資料來源**：halt 紀錄表。

| 分數 | 條件 |
|---|---|
| 5 | 0 次 |
| 4 | 1 次 |
| 3 | 2 次 |
| 2 | 3–4 次 |
| 1 | ≥ 5 次 |

### 5-2 未到達 done 的次數 · 重要 · Rubric

- **量法**：
  - 數一輪中用 recipe 重播、沒有跑到 done 的次數。
  - 對照組：E-1 的抽樣任務，不用 recipe、由 agent 自行把資料與畫面準備好，記錄成功與否。
- **資料來源**：execute session 紀錄、對照組。

| 分數 | 條件 |
|---|---|
| 5 | 0 次 |
| 4 | 1 次 |
| 3 | 2 次 |
| 2 | 3–4 次 |
| 1 | ≥ 5 次 |
| 上限 | 抽樣任務中，對照組成功、用 recipe 卻沒跑到 done 的任務 ≥ 1 個 → 最高 2 分 |

### 5-3 每步一次通過率 · 一般 · Rubric

- **量法**：每步一次通過率 = 不需 retry 就通過的步驟數 ÷ 執行的步驟總數。步驟包含 ensureContext 與 switchTab。
- **資料來源**：execute session 紀錄。

| 分數 | 條件 |
|---|---|
| 5 | 通過率 ≥ 98% |
| 4 | 95% ≤ 通過率 < 98% |
| 3 | 90% ≤ 通過率 < 95% |
| 2 | 80% ≤ 通過率 < 90% |
| 1 | 通過率 < 80% |

## 知識庫

目的：同一個坑不會被第二個 agent 再踩一次。

### K-1 重複踩坑次數 · 關鍵 · Rubric

- **量法**：
  - 坑：某條 route 在某個任務中需要讀程式碼才找到，或進入方式判錯。
  - 重複：同一條 route 的同一種坑，在已經發生過一次之後又發生。先前各輪發生過的坑也算「已經發生過」。
  - 數一輪中重複的次數。
- **資料來源**：transcript、route 對照、歷輪的坑紀錄。

| 分數 | 條件 |
|---|---|
| 5 | 0 次 |
| 4 | 1 次 |
| 3 | 2 次 |
| 2 | 3–4 次 |
| 1 | ≥ 5 次 |

### K-2 命中率曲線 · 重要 · Rubric

- **量法**：
  - 命中：階段 2 透過 routes recent／find 或 data-source get 找到既有紀錄，不用讀程式碼。
  - 依任務順序把任務集均分成前、中、後三段，各算命中率。
  - 上升幅度 = 後段命中率 − 前段命中率（百分點）。
- **資料來源**：routes／data-source／list 回傳。

| 分數 | 條件 |
|---|---|
| 5 | 上升幅度 ≥ 20 百分點，且後段命中率 ≥ 80% |
| 4 | 上升幅度 ≥ 20 百分點，且後段命中率 < 80% |
| 3 | 10 ≤ 上升幅度 < 20 百分點 |
| 2 | 0 < 上升幅度 < 10 百分點 |
| 1 | 上升幅度 ≤ 0（沒有累積效果） |

### K-3 命中時的效益 · 重要 · Rubric

- **量法**：節省比例 = (未命中任務在階段 2 的 token 中位數 − 命中任務的中位數) ÷ 未命中任務的中位數。
- **資料來源**：transcript。

| 分數 | 條件 |
|---|---|
| 5 | 節省比例 ≥ 70% |
| 4 | 50% ≤ 節省比例 < 70% |
| 3 | 30% ≤ 節省比例 < 50% |
| 2 | 10% ≤ 節省比例 < 30% |
| 1 | 節省比例 < 10% |

### K-4 被推翻率 · 重要 · Rubric

- **量法**：
  - 分母：階段 2 讀到、並實際用來導航的 data-source-map／route-catalogue 紀錄數。
  - 分子：其中被同一任務的實際觀察推翻、之後被 set 覆寫成不同值的紀錄數。
- **資料來源**：data-source-map、route-catalogue 的變更歷史（需補紀錄）。

| 分數 | 條件 |
|---|---|
| 5 | 被推翻率 ≤ 2% |
| 4 | 2% < 被推翻率 ≤ 5% |
| 3 | 5% < 被推翻率 ≤ 10% |
| 2 | 10% < 被推翻率 ≤ 20% |
| 1 | 被推翻率 > 20% |
